# Repair a repeated permission-check loop

For the agent. Use when the human says permission setup is looping, asks to “excise” a repeated instruction, or the same check returns after a pause without a relevant change. Stop the repeated operation now. This is a bounded review and proposed correction of the records driving that behavior, not permission to change settings, revoke access or purge memory. The latest kit may differ from installed instructions or summaries; a kit update alone does not repair those records.

## 1. Identify the repeating instruction

Use what the human already reported and the current conversation. Name the repeated action, its last observed outcome, and why it was proposed again. Distinguish an expected disposable-test denial from an unexpected denial of a real action. Do not run another probe to diagnose the repetition. If the cause is not visible, say so; a suspected stale summary is not a proven cause.

Before reading local records, state the bounded set and use existing read authorization for this purpose; ask only for a missing scope. Inspect:

- The installed instructions actually loaded by this session, including a user-level override only if it is known to affect this project and its read is authorized.
- The newest handoff by date and numeric sitting sequence, or the human-supplied continuation note when no saved handoff exists.
- The permissions ledger's current facts, check attempts and relevant grants/superseding entries.
- The memory index and only relevant linked memories about this setup, permissions or repeated behavior. Follow explicit references to an older local record only when it still supplies an active instruction and that read is authorized.
- The installed `kit/PIN` and relevant local setup/check rules. Compare with a newly published rule only after a separately authorized fetch; do not assume a downloaded ZIP or homepage pin updated this installation.

Do not search unrelated projects, accounts, all past chats or the whole memory store. Do not enter the app's private memory store or change global preferences by default. If a known active record is inaccessible, list that unresolved source; do not call the review complete. An inaccessible record does not require another attempt to read it through a denied route.

## 2. Separate directives from evidence

For each relevant passage, identify whether it is:

- A genuine observed result or current limitation to retain.
- A still-valid permission rule to retain.
- A stale or unsupported instruction to repeat, revoke, restart, or “keep checking until safe.”
- An unresolved question that needs evidence, not another automatic test.

Compare the directive with the actual folder, mode, protective rule and execution route, using available authorized evidence. A new chat, a different summary, an old incomplete checklist or an inconclusive result alone does not invalidate a passed check or justify retrying a failed one. Updating prose is not repairing an app boundary. Preserve genuine failures, unknown protection, approvals and grants; do not turn “unverified” into “passed,” remove a deny, or manufacture consent to make setup look finished.

## 3. Propose one coherent correction

Show the exact before-and-after and path for each active record that would change, with one short reason per change. Keep unrelated content. Do not delete whole records, wipe history or purge every mention of a failure. Remove or replace the obsolete *directive* in editable instructions, current handoff and relevant memory/index text; retain a concise historical fact if still needed. In the permissions ledger, append a superseding entry rather than rewriting old approvals or check outcomes. For an immutable old handoff still explicitly used by the current one, remove or replace the current dependency and explain the supersession; do not rewrite every historical handoff.

The correction should say which checks already passed, which route remains blocked or unverified, what event would justify reconsideration, and one useful next action outside the stopped route. For example, only if supported: “The shell boundary check could not reach the native gate; protected writes remain unavailable. Do not repeat it until the approved rule/tool change is verified. We can work in chat meanwhile.” Do not prescribe a successful file-write alternative before its own boundary is known.

Preview the bounded batch, including any memory-index change, and wait for approval under the existing edit/memory rules. A request to review or “excise” does not approve unseen replacement text. Installed instructions, kit and ledger remain protected by `templates/instructions.md`; a memory correction follows `stage1/03-memory.md`. A settings change or revocation is a separate proposal, not part of this text repair.

If a protected write is denied or its gate is unverified, leave it unmade. Offer the approved exact text for the human to apply, or pause that repair; do not change tools, permissions or writable roots to bypass the boundary. Say which active copies still contain the directive. Unsaved corrections govern this conversation only; they cannot be promised in a fresh one.

## 4. Verify the correction and resume useful work

After approved edits, re-read each changed record and check the bounded active sources for conflicting repeat directives, dangling pointers and the agreed stopping condition. If a batch partially failed, report the exact partial result and remaining active copy; no claim of complete repair. Do not run disposable denial probes merely to verify a wording edit.

Stop following the obsolete directive in this conversation; retain all real safety gates. Return to the human's chosen task or offer chat-only help. Do not force a new chat as the fix. If the human chooses one, provide a short reviewed continuation identifying corrected records, unresolved sources, blocked routes and the next action—not “repeat setup until it passes.” Reading corrected text can reduce its reinforcement in a fresh context; this does not erase provider-held chats, hidden summaries or inaccessible app memory. Never promise that all copies were purged or that recurrence is impossible.

## Done when

- [ ] The repeated action stopped; no further probe, revocation or restart was used to diagnose it.
- [ ] Authorized active records were inspected within a stated bound, or missing scope/inaccessible sources were reported.
- [ ] Stale directives were distinguished from valid rules, approvals, observed failures and unknowns.
- [ ] Exact bounded edits and pointers were approved before writing; protected boundaries held, ledger history was preserved, and partial/unsaved changes were identified.
- [ ] Changed records were reread and active conflicts checked; blocked routes stayed blocked and no privacy-erasure or universal-purge claim was made.
- [ ] The human received a useful next action without another automatic audit or forced reopen.
